# Emmy × 内测 BUG 闭环工作流

> 让 Emmy 把内测群收集的 BUG 收拢成「工单」，移交给代码侧的 Claude Code 自动修复，
> 每修好一条就 **@ 提出该 BUG 的人** 来验收。这是「飞书侧 agent + 代码侧 agent」协作的完整闭环。

---

## 一、全景

```
内测群发现 BUG
   │ (你的多维表格机器人收集)
   ▼
多维表格【工单看板】◀───────────────────┐
   │  Emmy 读 + 整理 + 写状态            │ worker 回写
   ▼                                    │ (待验收 + PR链接)
🦊 Emmy（飞书侧）                  🔧 修复 worker（代码侧）
   │ 标「待修复」+ 派工通知              ▲ 读「待修复」→ 切分支改代码 → 提 PR
   └──────────────表格───────────────────┘
   │
   ▼ worker 修好后，Emmy 检测到「待验收」
@提问人：你提的 #0009 修好了，PR 在这，请验收  ──▶  人 review PR → 标「已验收」
```

## 二、三个角色

| 角色 | 是什么 | 职责 |
|------|--------|------|
| 🦊 **Emmy** | 飞书侧 agent（已上线） | 读表格、整理分类、改状态、@提问人通知 |
| 📊 **多维表格** | 工单看板（单一事实源） | BUG 内容 + 状态流转都在这 |
| 🔧 **修复 worker** | 代码侧 agent（**待建**，≈ 另一个 Emmy） | 读「待修复」→ 在目标仓库改代码 → 提 PR → 回写状态 |

> **关键**：Emmy 不直接钻进代码仓库改代码。两个 agent **只通过表格通信**——一个管飞书、一个管代码，各司其职。

## 三、表格字段（在现有 BUG 表上加）

现有：`问题编号` `提问人` `提交时间` `问题摘要` `类型` …

**新增**：

| 字段 | 类型 | 谁写 | 说明 |
|------|------|------|------|
| `状态` | 单选 | Emmy / worker | 待处理 → 待修复 → 修复中 → 待验收 → 已验收 / 不修 |
| `负责人` | 文本 | Emmy | 可选，派给谁 |
| `修复分支/PR` | 文本 | worker | 回写 PR 链接 |
| `AI备注` | 文本 | Emmy / worker | 处理说明 / 修了啥 |

> `提问人` 受限于你的表格机器人只能写**文本名字**（写不了人员字段），@ 时靠群成员匹配反查 open_id（见 §六）。

## 四、分三步落地（别一口吃成胖子）

### ✅ 阶段 1（现在就能做）：Emmy 当「BUG 管家」
**不依赖 worker**，Emmy 先帮你把表格管起来——已经验证她能读表格 + 整理分类，再加「改状态 + @提问人通知」：

- `@Emmy 整理下大家提的 BUG` → 读表格、分类、小结（**已 work**）
- `@Emmy 把 #0009 标成待修复，通知提问人` → Emmy 改状态字段 + @ 提问人"#0009 已登记，安排修复中"
- `@Emmy 把已修好的都通知对应的人验收` → 逐条 @ 提问人

### 阶段 2：修复 worker（最重的一块）
目标仓库（MASS 代码）里跑一个 worker，**架构复用 Emmy**（`claude_runner` + `lark-cli`），只换触发源和工作目录：
- 轮询表格找 `状态=待修复` 的记录
- `cd 目标仓库 && claude -p "修复 #0009：<问题摘要>"` → 在**分支**上改代码
- `git push` 提 **PR**（绝不直接合主干）→ 回写 `状态=待验收` + `修复分支/PR`

### 阶段 3：闭环验收
Emmy 检测到 `状态=待验收` 的新记录 → 群里 @ 提问人 + PR 链接 + 请验收 → 人 review、合并 → 标 `已验收`。

## 五、各环节 lark-cli 命令（已核实）

```bash
# 读 BUG（列/搜表格记录）—— 需要 app-token(Base) + table-id（从表格 URL 或 lark-cli base 拿）
lark-cli base +record-list   --app-token <bascn_xxx> --table-id <tblxxx>
lark-cli base +record-search --app-token <bascn_xxx> --table-id <tblxxx> --params '{"filter":...}'

# 改状态字段（批量更新记录）
lark-cli base +record-batch-update --app-token <bascn_xxx> --table-id <tblxxx> \
  --params '{"records":[{"record_id":"rec_xxx","fields":{"状态":"待修复"}}]}'

# 列群成员（拿 open_id + 名字，用于 @）
lark-cli im chat.members get --chat-id <oc_xxx>

# @ 提问人发消息（飞书 text 消息的 at 格式）
lark-cli im +messages-send --as bot --chat-id <oc_xxx> --msg-type text \
  --content '{"text":"<at user_id=\"ou_xxx\"></at> 你提的 #0009 修好了，PR: <链接>，麻烦验收~"}'
```

> 具体参数实现时 `lark-cli <命令> --help` 查；先用 `--dry-run` 验证再真发。

## 六、@ 提问人怎么做到（提问人是文本名字）

```
1. lark-cli im chat.members get  → 拿这个内测群的成员（open_id + 名字，就几个人）
2. 让 Emmy 把 BUG 的「提问人」文本名 智能对上群成员（"齐凯-Kai Qi"→"齐凯"她能认）
3. 对上 → <at user_id="ou_xxx"> @ 他
```

**健壮性红线**：

| 匹配结果 | 怎么办 |
|---|---|
| ✅ 对上唯一群成员 | `<at>` @ 他，精准到人 |
| ⚠️ 对不上 / 多个重名 | **退回纯文本**："提问人 **王文胜**，你提的 #X 修好了…" |

@ 错人比不 @ 更尴尬——对不上就老实写名字。（Emmy 人设本来就写了"绝不瞎猜乱来"。）

## 七、三条红线

1. ⚠️ **AI 改代码必须走 PR + 人验收，绝不自动合进主干。** "通知验收" = "我改好了提了 PR，请你看"，不是"已修复完成"。
2. ⚠️ **Emmy 和 worker 是两个独立 agent，只通过表格通信。** 不混在一起。
3. ⚠️ **@ 不准就纯文本，绝不 @ 错人。**
